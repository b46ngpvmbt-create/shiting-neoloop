## 二、命题场景、公开事实与待验证问题

### 2.1 公开事实

新石器准时达 App 的公开版本记录出现过车辆事件、故障与运维工单、任务和服务质量评价；NeoClaw 相关版本说明还提到车队管理、日常运营和智能客服。来源见 [新石器准时达 App](https://apps.apple.com/cn/app/%E6%96%B0%E7%9F%B3%E5%99%A8%E5%87%86%E6%97%B6%E8%BE%BE/id1634537493)，核查日期为 2026 年 8 月 1 日。

北京经济技术开发区政府官网对 NeoClaw 的报道提到查车、发车、批量车辆控制、充电调度、数据查询和经营分析。报道同时说明，车辆物理控制需要身份、权限和车辆唯一性校验。来源见 [北京经济技术开发区政府官网的一手报道](https://kfqgw.beijing.gov.cn/ywdt/gdcyfzgd/zncx/202604/t20260413_4580756.html)，核查日期为 2026 年 8 月 1 日。

公开合作资料还显示，无人配送服务会涉及城市伙伴、专家支持和维修网络。来源见 [新石器城市合伙人合作方案](https://www.neolix.cn/cooperative) 与 [新石器和途虎的售后维保合作公告](https://www.neolix.ai/en/news/tuhu-partnership/)，核查日期为 2026 年 8 月 1 日。

这些资料能证明相关入口、数据对象和协作角色公开存在，但不能证明新石器内部目前缺少统一的反馈闭环，也不能据此推断企业现有系统架构。

### 2.2 待企业验证

我们把问题收在四个需要现场回答的事项上：

1. 不同入口产生的反馈，是否已经使用统一案件编号管理。
2. 反馈与车辆、任务、站点、版本和历史事件之间，哪些关联字段可以合法读取。
3. 客服、运营、技术支持、城市伙伴和维修网络之间，采用什么责任矩阵、SLA 和升级路径。
4. 案件关闭后，同类问题是否进入问题簇、改进项目和复发观察。

石听 NeoLoop 不预设这些问题的答案。方案先给出可配置的数据契约、工作流和验收方法，再由企业字段、权限和业务规则决定实际配置。

### 2.3 方案切入点

NeoLoop 从反馈进入企业后的协同环节开始工作，范围避开 NeoClaw 已公开的车辆操作和经营问答。反馈原文先留存，再关联车辆、任务和站点候选；证据不足的地方直接显示，由有权限的人确认。案件处理结果随后回到问题簇和改进项目。

## 四、五个创新点与现有证据

### 4.1 实体关联要能说明依据

N4 返回车辆、任务和站点候选，每个候选都列出证据、缺失项和置信度。正式实体关系仍由授权人员确认。本地合成工程测试已经覆盖 N4、N6、W3 和 W4 的契约及安全边界；赛事飞书中的字段可用性和人工确认记录属于现场验收项。

### 4.2 同事件并案与跨事件聚类分开处理

同一事件的重复反馈可以成为并案候选。不同事件即使相似，也只能进入同一问题簇，不能被合并成一个案件。每条反馈和每次处置因此保留独立记录。当前公开快照提供一条合成主故事和四类故障定义，场景状态仍为 `not_run`。

### 4.3 规则和权限先于模型建议

冲突处理顺序固定为硬规则、权限规则、经人确认的主数据、AI 建议。AI 可以建议提高风险等级，不能自行降低更高的规则结果。风险降级、正式实体、责任人、回复、结案、最终根因和知识发布都保留人工关口。

### 4.4 四类失败都有固定停点

同键重试不能覆盖旧记录，ID 缺失不能编造实体，AI 输出不合结构只能同版本重试一次，SLA 超时不能重置原计时。每条失败路径都要求保留原状态、错误分类和人工接管信息。四类公开故障目前是合成演练定义，不写成已经通过的现场结果。

### 4.5 案件关闭后转入同类问题观察

案件关闭后，W6 把不同事件组织为问题簇候选。N6 提出根因假设，同时保留支持证据与反证；问题负责人审核后才能建立改进项目。7 天和 30 天观察必须标注真实时钟、测试时钟或合成历史时间戳；没有业务量分母时只报告复发案件数。

## 五、单案闭环与改进闭环

### 5.1 合成主故事 `SYN-CASE-017`

合成输入为：“A 站取货时舱门连续两次无法解锁，任务已经延误。”公开快照版本为 `1.0.0-t1-r3-public.1`，fixture 版本为 `1.0.0-t1-r2`。该场景只用于说明流程，公开记录的执行状态是 `not_run`。

单案路径设计如下：

1. W1 保存原文和来源，计算幂等键。相同键再次接入时返回已有反馈，不新增业务记录。
2. W2 先执行硬规则，再调用 N1、N2、N3 生成事实、分类和风险建议。字段不足时进入人工处理或待补充。
3. W6 的同事件模式只产生重复候选，由人决定并案或保留独立案件。
4. N4 产生实体候选。N6 的责任路由模式产生责任候选。两项决定分别确认，不能用一次点击代替。
5. W3 在实体、责任和 SLA 规则版本确认后创建工单。W4 负责接单、提醒、升级和处置轨迹，改派不重置原 SLA 起点。
6. W5 校验证据并调用 N7 生成回复草稿。回复发布、回访结果和结案都需要授权人员确认。
7. 案件关闭后，W6 的跨事件模式才会提出问题簇候选，进入另一条改进闭环。

R4 本地合成内核已覆盖 N7 三种草稿模式、W5 证据验证与回访，并用 `SYN-CASE-017` 跑完 W1、W2、W6 同事件检查、W3、W4 和 W5 的单案脚本。本地用例 126/126、跨契约用例 4/4，full 为 130/130。这些证据只适用于单进程 scripted fake、in-memory repository、合成数据和测试时钟，不代表公开主故事回放、赛事飞书、真实 LLM、企业 IAM 或客户送达已验证。W5 并发回归只证明单进程同步原子段，不是数据库事务或分布式保证。W6 跨事件聚类、问题簇、改进项目与观察窗仍未实现。

### 5.2 改进闭环

不同事件进入同一问题簇后，系统保存成员案件、聚类版本、根因假设、支持证据和反证。问题负责人审核后才可立项。措施执行完毕后进入观察状态，7 天和 30 天检查使用明确的时钟来源。归档后出现新的同类案件，可以重新进入观察，但必须留下复发案件和人工决定。

公开快照中的 10 个改进项目均为合成设计快照，7 天结果、30 天结果和人工结论为空。正文只用它们说明数据结构，不把它们写作企业已经实施的改进或经营成果。

## 六、一个 Base、七个 AI 节点和六条工作流

方案把业务编排分成反馈理解、案件协同和改进洞察三个逻辑角色。它们不维护独立会话或权限，交接都通过 Base 中的稳定 ID、状态和运行记录完成；真正单独测试的是下面七个 AI 节点。

### 6.1 十张关联表

| 表 | 主要职责 |
| --- | --- |
| 原始反馈 | 保存不可覆盖的原文、来源、授权范围、幂等键和处理状态 |
| 反馈案件 | 保存摘要、分类、风险、缺失项、实体候选、正式实体、状态和 SLA 起点 |
| 处置工单 | 保存承接团队、责任人、动作、到期时间、证据、验证和升级信息 |
| 问题簇 | 保存成员案件、聚类版本、根因假设、支持证据、反证和审核状态 |
| 改进项目 | 保存措施、负责人、观察窗、时钟来源、指标公式和人工结论 |
| 车辆档案 | 保存关联所需的车辆快照，不提供车辆控制动作 |
| 配送任务 | 保存车辆、站点、路线、任务状态和来源时间，仅作为关联证据 |
| 站点责任矩阵 | 保存区域、站点、问题类型、默认团队、审核人、升级路径和 SLA 版本 |
| 知识索引 | 只索引经过人工审核的 SOP 与答复模板 |
| AI 审计 | 保存对象引用、节点、模式、版本、输入哈希、校验、重试和人工决定 |

前台只展示反馈收件箱、案件驾驶舱、SLA 协同板、问题地图和改进追踪五个视图。车辆、任务、责任矩阵、知识索引和 AI 审计留在管理员视图。

### 6.2 七个 AI 节点

| 节点 | 输出 | 不可越过的边界 |
| --- | --- | --- |
| N1 结构化抽取 | 原文事实、诉求、对象线索、缺失项 | 每条事实必须指向原文片段 |
| N2 业务分类 | 业务域、二级类别、标签、置信度 | 分类词典必须带版本 |
| N3 风险建议 | 风险建议、触发证据、解释 | 不能覆盖更高的硬规则风险 |
| N4 实体关联 | 车辆、任务、站点候选及逐项证据 | 不能写入正式关系 |
| N5 重复识别与聚类 | 同事件重复候选或跨事件问题簇候选 | 两种模式不能互相写入结果 |
| N6 根因假设与责任路由 | 责任候选或根因假设、支持证据、反证 | 不能输出最终责任或最终技术根因 |
| N7 回复、知识与洞察草稿 | 三种模式的草稿和已审核引用 | 未经人审不能发布 |

AI 输出统一使用结构化 envelope，记录节点、模式、版本、运行 ID、对象引用、输入哈希、证据、缺失项、置信度和校验结果。输出不合结构时，只允许同版本修正重试一次；再次失败即停止节点链并转人工。

### 6.3 六条工作流

| 工作流 | 作用 | 人工关口或失败处理 |
| --- | --- | --- |
| W1 接入幂等 | 保存原始反馈，阻止同键重复写入 | 同键异内容拒绝覆盖 |
| W2 风险分诊 | 运行硬规则与 N1 至 N3，创建案件 | 节点失败后转人工处理 |
| W3 关联派单 | 调用 N4 与 N6，确认后创建工单 | 正式实体和责任分别确认 |
| W4 SLA 协同 | 接单、提醒、升级、接管和处置轨迹 | 超时或通知失败时保留原状态与原计时 |
| W5 验证与回访 | 核验证据、生成回复草稿、记录回访 | 回复、退回、关闭由授权人员决定 |
| W6 问题簇与复发监测 | 同事件检查、跨事件聚类、改进和观察 | 并案、根因、知识发布、归档与重开均需人审 |

赛事环境中的 Base、字段、视图、AI、自动化、审批、通知、知识库、妙搭、Aily、lark-cli 和 OpenAPI 都列为现场验收项。离线配置包和本地测试不能替代这些证据。

## 七、四类故障与安全降级

| 合成故障 | 预期安全路径 | 当前证据状态 |
| --- | --- | --- |
| 同一幂等键重试，同时提交异键相似文本 | 同键回放已有结果；异键创建独立记录，等待人工并案判断 | 定义已冻结，公开场景 `not_run` |
| 删除车辆 ID 和任务 ID | 案件停在待补充，不编造 ID，不写正式实体 | 定义已冻结，公开场景 `not_run` |
| N4 输出缺少必需 envelope 字段 | 同版本最多重试一次，再失败则停止节点链并交给人工 | 定义已冻结，公开场景 `not_run` |
| 用测试时钟模拟 SLA 超时 | 发起升级和人工接管，保留原状态、原起点和原到期时间 | 定义已冻结，公开场景 `not_run` |

系统永远不执行车辆控制，不自动降低高风险，不自动判定事故责任、赔偿、恢复时间或最终技术根因，也不自动发布客户回复和知识条目。

## 八、方案价值、合成对照与企业复测

### 8.1 当前可以核验的内容

canonical 数据与公开快照已通过 23/23 数据测试。公开快照包含 14 个文件、30 条反馈索引、20 个案件、27 张工单、10 个问题簇、10 个改进项目、1 条主故事、4 类故障和 5 个只读视图，全部标记为 `synthetic_experiment`。R4 工程内核测试为 local 126/126、cross 4/4、full 130/130，只覆盖本地单进程 scripted/in-memory 环境。赛事飞书离线探针包通过 213/213 结构检查，但 P01 至 P13 的现场结果仍为 `not_tested`，不能把离线检查写成平台能力通过。

### 8.2 合成流程对照实验

对照实验设计使用冻结的 20 个合成案件。每个案件分别执行人工 SOP 和 NeoLoop 流程，并用固定随机种子分成 AB、BA 两组，减少先后顺序带来的学习影响。原始记录包括操作者、顺序、开始与结束时间、人工操作次数、证据遗漏、路由修改和高风险漏检。

只有原始记录、样本量、中位数、范围和错误样例都齐全时，文档才展示处理用时、证据遗漏、路由修改和人工操作次数的比较结果。当前不预填节省比例、效率提升、收入或 ROI。

### 8.3 企业复测方法

| 指标 | 计算方法 | 企业复测前置条件 |
| --- | --- | --- |
| 首次响应时长 | 首次人工响应时间减去反馈接入时间 | 企业确认计时起点和真实基线 |
| 证据完整率 | 满足必填证据的结案申请数除以全部结案申请数 | 企业确认各类案件的证据清单 |
| 责任路由准确率 | 路由正确案件数除以有人工金标准的案件数 | 企业提供责任矩阵和真实标注 |
| P0/P1 风险召回率 | 正确识别的高风险案件数除以全部高风险标注案件数 | 企业确认风险定义和案例 |
| SLA 按时完成率 | SLA 内完成工单数除以到期工单数 | 企业确认 SLA、节假日和升级规则 |
| 问题复发率 | 观察窗同类案件数除以同期相关任务量 | 企业提供同口径任务量分母；没有分母时只报复发数 |

合成流程实验只验证机制，不能外推为新石器的真实效率或经营收益。

## 十、自由展示区：一条故事看懂两条循环

自由展示区不另造第三套软件，而是把 Web、飞书和离线证据按不同层级组织成一条可追溯的合成故事：

`SYN-CASE-017 → SYN-CLUSTER-001 → SYN-IMPROVEMENT-001`

### 10.1 全渠道接入不是人工录表

方案入口覆盖 App、客服系统事件、经授权热线转写、授权服务邮箱、飞书群或表单，以及经授权公开平台。各入口通过官方 API、Webhook 或事件合同进入不可变原始反馈池；真实接入仍以企业授权、字段确认和最小权限为前置条件。公开 Web 只解释接入合同，不发送任意文本、不调用真实接口、不保存数据。

### 10.2 90 秒双循环交互

Web 的 `#dual-loop` 区域允许评委点击 11 个步骤，逐项查看输入、AI 作用、证据、人工关口和预期输出：

- 个案闭环：接入幂等 → AI 分诊 → 实体关联 → 人工确认 → 工单与 SLA → 回访关闭。
- 改进闭环：跨事件聚类 → 根因假设 → 人工立项 → 7/30 天观察 → 归档或复发重开。
- 回流规则：个案关闭后进入改进观察；出现复发时返回处置与改进，但不覆盖旧记录。

五类视觉图例固定为 AI 候选、确定性工作流、硬规则、人工关口和证据状态。Web 中的所有交互只改变当前浏览器状态。

### 10.3 参数化价值测算

`#value-lab` 使用可公开复核的公式：

`月反馈量 × max（当前人工分诊耗时 − 辅助后分诊耗时，0）÷ 60`

默认合成假设为 1000 条/月、8 分钟/条降至 3 分钟/条，对应理论释放 83.3 小时/月。评委可以修改三项参数；该结果不代表新石器真实业务基线、成本节省、收入或 ROI。

### 10.4 可复现工程证据

离线评委体验包包含打开说明、10 页视觉附录、三份 Excel、10 表 240 字段 Base 导入样例、静态双循环图、视频、链接清单和 SHA-256 校验值。压缩包不包含完整工程目录、依赖、私有配置、OAuth 信息、飞书资源 ID、内部证据或失败暂存目录；源码只提供公开 GitHub 链接。

## 十一、工程补充、推广映射、来源与团队说明

### 11.1 CLI 与 OpenAPI

方案中的项目 CLI 按固定命令设计，范围包括能力检查、schema diff、dry-run、种子校验与导入、反馈接入、AI 与工作流评测、证据导出。命令约定使用 JSON 输出和稳定退出码。lark-cli 只有在赛事环境确认允许使用并完成登录、scope 和能力检查后，才参与现场操作。

OpenAPI 接入设计为 `POST /v1/feedback`，要求时间戳、nonce、HMAC 签名和幂等键。同键同内容返回已有记录，同键异内容返回冲突，不覆盖旧记录。该服务默认不公开启用；只有自建应用、管理员审批、最小权限和独立密钥存储都通过后才可使用。
