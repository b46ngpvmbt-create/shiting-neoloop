## N7 实现边界

- 三个模式固定使用 `N7-1.0.0-draft.2`，输入统一为已审核事实、已验证处置结果和已审核知识索引。
- 输出统一使用结构化字段：草稿种类、草稿正文、知识引用、支持证据、未发布状态、人工审核要求和禁止自动发布标志。
- mode、version、object reference 和 input hash 由现有 runner 绑定；Schema 修正最多重试一次，第二次仍失败即返回人工处理，并为每次实际尝试写 AI 审计。
- `customer_reply` 必须引用知识索引中 `已审核`、有版本、有效时间可解析且允许 N7 引用的记录；引用必须绑定同一 `knowledge_id + version` 及对应知识证据。
- 三种模式都必须同时引用已审核事实和已验证处置结果。额外、越界、未引用、提示注入或无法在输入中定位的证据均被拒绝。
- 输出永远是 `draft_unpublished`；N7 不发送客户回复，不发布知识，不写正式结论，不获得工具能力。

## W5 实现边界

- W5 命令使用闭集 action 和 exact own-data shape；继承字段、额外字段、symbol、accessor、异常 prototype 或自报授权字段在授权前拒绝。
- 边界校验通过后立即深拷贝并重新校验权威命令快照；事件指纹、授权、N7、状态转换和审计只使用这份快照，不继续引用调用方的可变对象。
- 每个动作都调用外部授权端口。正式回复审核、回访和关单记录保存规范化 principal 与授权策略版本，命令中的 actor 声明本身不构成权限。
- 授权端口必须返回由同一进程内 WeakMap 通道签发的一次性 opaque grant。grant 同时绑定 workflow、event、case、work order、action、target fingerprint、command fingerprint、principal 和 policy；错误通道、任一 claims 不匹配、伪造或重放都在领域写入前失败。
- 证据不足会保存不完整提交，案件和工单保持“处理中”，SLA 不变，N7 不运行；补充证据必须引用已保存的不完整提交。
- 证据完整后只调用 N7 `customer_reply`。成功时保存未发布草稿并进入“待验证”；N7 两次结构失败时保存处置证据、保持“处理中”并转人工。
- 回复审核通过只记录人工审核和手动送达引用，W5 本身不调用发送端口；退回时保留已有证据和草稿并回到“处理中”。
- 正常回访进入关单人工门；异常回访回到“处理中”。关单可以关闭或退回，两个决定都要求授权端口通过并保存人工决策证据。
- 状态转换同时校验 `status` 与 `workflow_readiness`，防止阶段不一致记录跨过证据、回复、回访或关单门。
- 案件、工单和 W5 历史通过一次原子 transition 写入；compare-and-set 失败不覆盖新状态。`sla_started_at`、`sla_due_at`、SLA 规则版本、工单到期时间和 `sla_reset_count=0` 全程保持。
- 进程内 repository 的 W5 commit 从 CAS 到历史附加、Map 写入和返回 receipt 不包含 `await`；因此 W4 改派要么在 W5 前完成并让 W5 冲突关闭，要么在 W5 后基于新值完成，不再发生两方都报成功却丢失改派的情况。这只是单进程 JavaScript 原子性，不是数据库事务或分布式保证。
- 同一 `event_id` 同内容复用已缓存结果；同 ID 异内容失败关闭。业务提交后的审计失败标记 `audit_pending / audit_failure_after_commit`，重放只补审计，不重复 N7、授权、人工决定或领域写入。
