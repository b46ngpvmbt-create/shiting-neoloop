## 完成项与证据

### N4 实体候选

- 版本化固定 N4 的 mode、version、input 和 payload 边界。
- 只输出 vehicle/task/station 候选，每项同时绑定案件事实和合成参考记录证据；未知 ID、缺 ID、多候选冲突或证据不足均失败关闭。
- N4 不写 `formal_entity`，不暴露工具端口，嵌套提示注入仅作为不可信数据处理。

### N6 `responsibility_routing`

- 只实现已批准的 `responsibility_routing`；未实现的 root-cause mode 在 invoker 前拒绝，生成 `error` envelope 并审计。
- 输入边界在 invoker 前检查责任矩阵字段、版本、`enterprise_pending / 待企业验证`、问题簇与匹配路由；伪造“已生效”的矩阵不进入 fake/LLM 调用。
- 每个匹配路由候选固定团队、逻辑角色、规则版本和 SLA 版本，必须同时有非空支持证据与非空反证。
- 反证必须绑定竞争路由的 rule/team/status，或本路由的待企业验证状态；不能用 `uncertainties` 替代。
- support/counter 不仅拒绝同 index 或完全复制，还拒绝同源全文/子串和原文区间相交，避免用一条事实伪装成正反两面证据。
- 单一匹配路由也有正向用例：support 绑定 rule/team 文本，counter 绑定同一 rule source 中独立、可定位且不重叠的“待企业验证”状态片段；不要求必须有第二条竞争路由才能进入人工门。
- N6 仅给候选团队与逻辑角色，不判责、不定赔偿、不承诺恢复时间、不指定最终责任人、不输出最终技术根因。

### W3 人工门与派单

- 运行顺序固定为：前半链完成 → W6 同事件候选处理 → N4 候选 → 实体确认门 → N6 路由建议 → 路由确认门 → 创建 `待接单` 工单。
- 实体确认和路由确认是两个独立持久化停点；多候选不自动选择，不自动连接正式实体，不重复建单。
- 工单 SLA 以不可变原始反馈 `received_at` 为起点，派单仅使用人工选定的 N6 候选。
- 平台现场投影边界未验证：`scenario_runtime` 工单在人工处置前使用 `disposition_evidence=null`，无 legacy 记录时使用 `legacy_recorded_at=null`。T2 manifest 的 required 目前只冻结字段配置，尚无现场空值 probe；真实落表前若平台拒绝空值，必须停点裁决，不得伪填 legacy 事实。

### W4 SLA 协同

- 实现接单、改派、提醒和超时升级；接单/改派必须经人工 actor 类型和 allowlist 端口，提醒/升级必须经合成 SLA workflow actor 授权。
- 空 ID、未知 action，以及 reassign/remind/escalate 各自缺少 team/role/message/level 的命令都在事件仓库和授权端口之前拒绝；授权拒绝与授权端口异常分别记为 `denied` 和 `indeterminate`，失败结果可保真回放。
- `sla_started_at`、`sla_due_at`、SLA 规则版本和 `sla_reset_count=0` 在改派、提醒、升级、重试或通知失败时不重置；提醒和升级不增加案件状态。
- 当前唯一获批准的升级路径是 `none → L1`；`none → L2`、`L1 → none/L2/L99` 全部失败关闭。L2 及之后必须等企业升级路径冻结，本轮不伪造。
- 升级通知使用 effect-aware compare-and-set：effect 前冲突不调用 notifier；effect 完成后的更新/删除冲突不覆盖外部状态，且审计明确记为 notifier `acknowledged`，不谎称“未发送”。删除分支返回当前 `work_order=null`、`work_order_snapshot_unavailable`，不再携带删除前快照或声称工单仍已保留。
- `Notifier.notify(): Promise<void>` 只能证明 fake/适配器调用被确认，不能证明终端到达。同 `event_id` 在同仓库实例内不重复调用已验证；跨新 event ID、进程崩溃、网络丢 ACK 或持久化恢复的 exactly-once 未验证，生产适配需 outbox 与幂等通知键。
