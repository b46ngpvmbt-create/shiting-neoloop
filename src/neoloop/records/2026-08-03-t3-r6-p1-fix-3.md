### GREEN 1：签发前守卫

仓储新增唯一共享函数 `violatesW6ActiveIntakeObservationWindow`。它固定以下语义：

- `opened_at < closed_at <= min(occurred_at, day30ExpectedAt)`；
- Day-7 在“同周期 checkpoint 已存在”或 `occurred_at > day7ExpectedAt` 时视为已封口；
- Day-7 已封口后，任何 `closed_at <= day7ExpectedAt` 的新 intake 均失败关闭；
- `closed_at > day7ExpectedAt` 且不超过 Day-30 的案件仍可作为 Day-30 recurrence source。

N5 action-scoped validation receipt 的仓储签发路径调用该共享守卫。第一阶段 GREEN 为 local 247/247。

### RED 2：receipt → checkpoint → commit 竞态

独立确定性用例按下列顺序执行：

1. 在尚无 Day-7 checkpoint 的观察状态内，为同毫秒旧案签发合法、action-scoped 的 N5 validation receipt，并创建与同一 event/command/target 绑定的人工授权 capability；
2. 用另一个事件在精确 `day7ExpectedAt` 抢先提交 Day-7 checkpoint；
3. 以 checkpoint 提交后的完整 durable state 为 `before`；
4. 恢复原事件，取得完整 case/cluster/improvement 资源锁，消费两个 capability，再尝试提交原 intake。

- RED 命令：`node tests/core/run-core-tests.mjs --local-only`
- RED 结果：248 项中 247 通过、1 失败。
- 首个错误：最终提交只报通用 `W6 active-observation recurrence intake command is invalid`，说明旧的 W6 state-fingerprint CAS 先于窗口守卫返回，测试不能证明 commit 重新执行共享 Day-7 语义。

### GREEN 2：最终提交守卫及零写入

最终提交仍保留 W6 state-fingerprint CAS，但在 active-intake 分支中先用同一共享函数重验权威 cycle、checkpoint 和 closed case，再执行 state-fingerprint CAS。该原子提交段没有 `await`。

竞态用例最终证明：

- commit 由共享窗口守卫明确拒绝；
- checkpoint 抢先提交后的案件、反馈、工单、索引、same-event、W5 记录及全部可见 W6 cluster/improvement/cycle/intake/checkpoint/history/receipt 均保持不变；
- 已消费的 N5 validation capability 和人工授权 capability 均不能重放；capability 消费是预期的私有安全状态，不冒充业务或 W6 durable 写入。

最终 local 为 248/248。

## P2：确定性 provider-await 证明

`w6-improvement.test.mjs` 不再用 50ms 超时竞争判定成功。测试现在：

- 包装同一 repository 的 `runW6ResourcesExclusive`，记录实际进入资源临界区的数量；
- provider 入口记录当时是否持锁并发出 `providerEntered`；
- 独立 lock probe 取得相同 case/cluster/improvement 锁后发出 `probeAcquired`；
- 按 `providerEntered → probeAcquired → probeRelease → providerRelease` 的确定顺序完成；
- 5 秒 test-level timeout 仅用于异常清理和防止测试进程永久挂起，不作为成功判据。

测试仍要求原 start 正常完成，且 provider await 期间资源临界区计数为 0。生产代码未因该 P2 调整。
